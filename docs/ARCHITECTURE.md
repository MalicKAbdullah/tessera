# Tessera architecture

Tessera is a Flutter app with a native Kotlin widget engine. The engine draws
every home-screen widget; the Flutter app is a catalog, an editor and a
preview window onto that same engine.

```
Flutter (lib/)                          Kotlin (android/app/src/main/kotlin/…/tessera)
─────────────                           ────────────────────────────────────────────
Gallery / Editor ── MethodChannel ──▶  EngineChannel ─▶ Registry (designs)
  catalog, render, pin, bind,           "tessera/engine"   │
  setContent, placed, specimen                              ▼
                                        Engine ─▶ Renderer ─▶ RemoteViews ─▶ launcher
                                          ▲         │ Scene (Canvas in dp + overlays)
                     providers, ticker,   │         ▼
                     workers, receivers ──┘      data/ (battery, weather, alarm, content)
```

## Engine (`engine/`)

| File | Role |
| --- | --- |
| `Model.kt` | `Category`, `SizeClass`, `Signal`, `Toggle`, and the `WidgetDesign` interface. |
| `Registry.kt` | The single list of designs, in gallery order, plus the catalog JSON for Dart. |
| `Slots.kt` | One `AppWidgetProvider` per category × size (`Slot`). |
| `Instances.kt` | Per-`appWidgetId` binding: design id + `Style`, and the last live key. |
| `Engine.kt` | Resolves an id to its binding, measures it, renders, and decides what to redraw. |
| `Renderer.kt` | Draws the surface and design into a bitmap, attaches overlays, returns `RemoteViews`. |
| `Scene.kt` | The drawing API a design gets: canvas in dp, paints, fitting, overlays. |
| `Style.kt` | v2 style JSON (mirror of `widget_style.dart`). |
| `Fonts.kt`, `FontTable.kt` | Bundled families and faces; `FontTable.kt` is generated. |
| `Live.kt` | Live ticker, workers, pin/tick/system receivers. |

Providers live in `widgets/Providers.kt` (package `…tessera.widgets`) because
v0.1 registered its providers under those class names; keeping them means
widgets placed on v0.1 survive the update. They hold no logic.

### How a widget is drawn

1. `Engine.render(id)` finds the slot (from the provider class), the binding
   (or the slot's default design when unbound) and the size in dp from
   `AppWidgetManager` options (`MIN_WIDTH` × `MAX_HEIGHT`, portrait). It
   re-renders on `onAppWidgetOptionsChanged`, so resizing redraws at the new
   size.
2. `Renderer` makes a bitmap at `min(density, √(900 000 / (w·h)))` px per dp.
   The cap keeps RemoteViews under the binder/bitmap budget; above it the
   ImageView upscales slightly.
3. The canvas is scaled so designs draw in dp. The style's surface (solid,
   gradient, dot grid, grain, transparent, photo) is painted and clipped to
   the corner radius, then `design.draw(scene)` runs.
4. Overlays the design declared are added as nested RemoteViews in
   `widget_frame.xml`'s overlay container, positioned by padding in px.

### Overlays: what makes widgets live without waking the phone

Android widgets cannot run code per frame. Tessera uses only what RemoteViews
supports natively:

| Overlay | Used for | Cost |
| --- | --- | --- |
| `Scene.textClock` → `TextClock` | Every time and date string. Minute-accurate (second-accurate for `ss`) with no alarms: the launcher ticks it. | None |
| `Scene.analogHands` → `AnalogClock` | Analog hands over a bitmap dial. Hand tint is remotable from API 31; earlier, light or dark prebuilt hands are chosen by luminance. | None |
| `Scene.flipper` → `ViewFlipper` (autoStart) | Short loops: LED pulse, charging fill, gauge glow, ripple. Frames are small bitmaps of just the moving region. | Runs only while the home screen is visible |

**TextClock and fonts.** RemoteViews cannot pass a `Typeface`, so each font
face has its own TextClock layout (`tc_<face>.xml`, and `tcc_<face>.xml` with
all caps), generated by `tool/gen_font_layouts.sh` together with
`FontTable.kt`. Size (`COMPLEX_UNIT_DIP`), colour, gravity, padding, format
and time zone are set remotely. Letter spacing is not remotable, so the
spacing control affects bitmap text only.

### Freshness

Everything a bitmap shows that no overlay keeps current is covered by a
**live key**: `WidgetDesign.liveKey(inputs)` returns a string describing what
the bitmap shows (e.g. `"83|true|AC"` for battery, `"14"` for an hour ruler).
The engine stores the key per instance and redraws only when it changes.

| Trigger | What happens |
| --- | --- |
| **Live ticker** (`LiveTicker`, ~1 min, `AlarmManager.RTC`) | Non-wakeup: never wakes the device, fires as soon as it wakes. Runs only while some placed widget has a live key. Replaces `ACTION_SCREEN_ON`, which manifest receivers cannot get. |
| **Charging trigger** (WorkManager, `requiresCharging`) | Armed whenever a battery design renders unplugged; runs the moment power connects. `ACTION_POWER_CONNECTED`/`DISCONNECTED`/`BATTERY_LOW`/`OKAY` are not delivered to manifest receivers since Android 8. |
| **Periodic refresh** (WorkManager, 15 min) | `Engine.tick`: redraws anything whose key moved. |
| **Weather** (WorkManager, 60 min, network) | Fetches Open-Meteo into the cache, then redraws `Signal.WEATHER` designs. Also runs once when the city changes and when the app opens with a stale cache (>30 min). |
| **App foreground** (`MainActivity.onResume`) | Redraws everything; a runtime battery receiver redraws on every level/plug change while the app is open. |
| **System events** (`SystemEventsReceiver`) | Boot, package update, time set, time zone and locale changes redraw everything. |

Data is read at render time (`data/Data.kt` is a lazy per-render bag), so a
bitmap is never older than the render that produced it. Battery comes from the
sticky `ACTION_BATTERY_CHANGED` intent plus `BatteryManager` (level, status,
plug type, temperature, voltage, health, `computeChargeTimeRemaining` on API
28+). `BatteryHistory` samples the level on each render/tick for 24-hour
charts and drain estimates.

### Previews are the widget

`EngineChannel.render` builds the exact `RemoteViews` the launcher receives,
inflates it with `RemoteViews.apply`, attaches it off-screen (TextClock and
AnalogClock only read the time once attached), draws the view tree and returns
a PNG. The gallery, editor, pin dialog (`EXTRA_APPWIDGET_PREVIEW`) and home
screen therefore show the same pixels.

### Placing and binding

- **From the app:** `pin` calls `requestPinAppWidget` on the slot for the
  chosen size with a mutable callback to `PinReceiver`, which binds the new id
  to the design and style.
- **From the launcher picker:** providers declare `ConfigureActivity` with
  `reconfigurable|configuration_optional`. On Android 12+ the widget appears
  immediately with the slot's default design and can be reconfigured by
  long-press; earlier, the configure screen opens first. The configure screen
  is the Flutter gallery filtered to the slot.
- **Editing a placed widget:** tapping a widget opens its editor; changes bind
  live (debounced).

## Customization model (`lib/src/features/widgets/models/widget_style.dart`)

`WidgetStyle` v2, shared verbatim with Kotlin:

```json
{"v":2,"font":"dot","weight":700,"scale":1.0,"tracking":0.0,
 "text":4294111467,"accent":4294947872,
 "bg":{"kind":"solid|gradient|dots|grain|transparent|photo","color":…,"color2":…,"angle":135,"photo":null},
 "opacity":1.0,"radius":30,"padding":16,"toggles":{"hours":"24","pulse":true}}
```

- **Weight** is any 100–900 value snapped to the nearest face the family
  ships (`snapWeight` in Dart, `Fonts.face` in Kotlin — same rule).
- **Toggles** are per design; a missing key means the design's default.
- **Migration:** a style without `v` is v0.1 and becomes v2 on read
  (`WidgetStyle.fromV1`: Inter Tight at the same weight, solid surface, 20dp
  padding). At first launch `migrateFromV1` turns each kind's v0.1 style into
  the draft of its successor design and binds widgets placed on v0.1.

Drafts (the style being tuned for a design before pinning) live in the app's
shared preferences; placed widgets own their binding natively.

## Adding a design

1. **Create** `designs/<category>/<Name>.kt` with an `object` implementing
   `WidgetDesign`:
   - `id` — `"<category>.<name>"`; stored per placed widget, never rename.
   - `category`, `name`, `blurb`, `sizes` (each needs a slot, see below).
   - `defaults` — `Style.of(font, weight, text, accent, background, …)`.
   - `toggles` — `Toggle.Switch` / `Toggle.Choice`; reuse `hourFormatToggle`
     for clocks. Read them with `s.flag(key)` / `s.choice(key)`.
   - `signals` — data it depends on (`BATTERY`, `WEATHER`, `CONTENT`, `ALARM`).
   - `liveKey` — only if the bitmap shows something time- or data-varying
     that no TextClock covers.
   - `motion` — one sentence if it uses a flipper; shown in the gallery.
   - `draw(s: Scene)` — draw in dp inside `s.box` (padding applied). Use
     `s.paint(...)` (style font, weight, tracking), `s.fit(...) * s.hero` for
     hero text, `size * s.k` for secondary text, `s.textClock` for anything
     showing the time or date, `s.flipper` for loops. Never leave a region
     empty: every state (no data, no permission, first run) must draw
     something meaningful.
2. **Register** it in `Registry.designs` (gallery order; the first design of a
   category that fits a slot is that slot's default).
3. **New data?** Add a `DataSource<T>` in `data/`, expose it lazily on
   `Data`, add a `Signal` if something outside a render changes it, and call
   `Engine.refresh(context, signal)` from whatever observes the change.
   Runtime permissions (e.g. calendar) are requested from Flutter; the
   source must draw a "grant access" state when denied.
4. **New category or size?** Add the `Category` entry, a provider class in
   `widgets/Providers.kt`, its `Slot` in `Slots.all`, an
   `res/xml/widget_<category>_<size>.xml` (copy an existing one), and a
   `<receiver>` in `AndroidManifest.xml`. `Registry` checks at start-up that
   every design size has a slot.
5. **Content controls** for a new category go in the editor's
   `_contentControls` switch (`editor_screen.dart`). Nothing else on the Dart
   side changes: the gallery, editor controls, toggles and previews all come
   from the catalog.
6. Pure layout or text logic gets a JVM test in `android/app/src/test`
   (see `EngineMathTest`).
